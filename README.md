# Codex Workspace Migration

[![Tests](https://github.com/LeoSasion/codex-workspace-migration/actions/workflows/tests.yml/badge.svg)](https://github.com/LeoSasion/codex-workspace-migration/actions/workflows/tests.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

面向 Windows 上 Codex 工作区迁移与归档的可复用技能。分别核验源码目录、聊天工作目录、资料访问范围和运行依赖，并通过 SHA-256 全量清单检查归档内容。

独立开源仓库：[LeoSasion/codex-workspace-migration](https://github.com/LeoSasion/codex-workspace-migration)。技能与校验工具均采用 [MIT 许可证](LICENSE)。本项目为社区技能，与 OpenAI 无隶属关系。

## 安装

需要 Git；运行目录校验器另需 Python 3.10 或更高版本，无第三方 Python 依赖。技能主要针对 Windows 桌面迁移；跨平台测试仅验证目录校验器，不代表 Codex 迁移流程在所有平台都已验收。

在 PowerShell 中克隆到个人技能目录；已存在同名技能时停止，先检查本地修改：

```powershell
$skillHome = if ($env:CODEX_HOME) { $env:CODEX_HOME } else { Join-Path $env:USERPROFILE '.codex' }
$skillTarget = Join-Path $skillHome 'skills/codex-workspace-migration'
if (Test-Path -LiteralPath $skillTarget) { throw '目标技能目录已存在，请先检查本地修改。' }
New-Item -ItemType Directory -Force -Path (Split-Path -Parent $skillTarget) | Out-Null
git clone https://github.com/LeoSasion/codex-workspace-migration.git $skillTarget
if ($LASTEXITCODE -ne 0) { throw '技能克隆未完成。' }
```

让 Codex 重新加载技能后，用 `$codex-workspace-migration` 调用。执行说明见 [SKILL.md](SKILL.md)，校验器用法见 [目录清单说明](references/tree-manifest.md)。

仓库只提供通用流程、参考文档和目录校验工具。它不携带原项目材料，也不会自动修改聊天配置、移动目录或操作服务。清单、备份、凭据与真实迁移回执始终保存在仓库之外。

## 匿名案例

本文记录 2026-10-17 一次项目迁移的教训。项目名称、域名、仓库地址、用户名、聊天标识和私有路径均已替换或省略。这里是背景与经验说明；执行时从 [SKILL.md](SKILL.md) 开始。

## 背景与环境

一个内部协作平台逐步形成了多个自研模块、集成组件和维护脚本。部分源码已经迁入统一仓库，但旧开发目录仍被多个聊天、已停止的验收容器和本机维护脚本引用。旁边还有一个只通过平台接口取数据的独立前端项目，以及一个独立研究资料目录。

环境包含 Windows、打包分发的 Codex 桌面应用、普通桌面 CMD／PowerShell、Python、Git 与 Docker Desktop。运行代码和业务数据主要位于容器及持久卷，旧开发目录混有源码、临时 Git 引用、凭据、证据和历史资料。用户会在几轮操作之间退出 Codex、更新应用或重启电脑，环境不是静止的。

因此，这次工作同时涉及文件系统、Git、聊天持久化设置、桌面缓存、容器挂载和 Windows 进程环境。它并不是一次简单的文件夹改名。

## 需求和目的

- 让统一仓库成为相关模块唯一的开发、构建与提交入口。
- 把相关聊天的实际工作目录切换过去，保留模型、审批策略和应有资料访问范围。
- 独立前端项目继续独立；研究资料保留为可访问来源，不默认复制到 Git。
- 对已获准退役的停止验收容器保留可恢复材料，解除旧目录的实际运行依赖。
- 完成核验后将旧目录同级改名归档，保留文件、私有证据和业务数据。
- 单独整理代码提交与推送，不把目录归档表述成部署或完整业务验收。

## 遇到的困难、错误与正确方法

| 问题 | 当时的错误或遗漏 | 应采用的方法 |
| --- | --- | --- |
| 项目入口与聊天 cwd 不一致 | 把侧栏移动成功当作工作目录切换；部分聊天仍在旧目录或研究目录执行 | 分别读取项目归属、持久 cwd、实际 cwd、来源目录和待应用状态；重开后再次验证 |
| 空闲聊天仍被锁住 | 只看是否正在生成，忽略桌面可能持有写入者 | 识别活动／已加载／未加载状态；完成在线准备后再释放确有必要的桌面锁，不删除锁文件 |
| 应用内路径能读，桌面 CMD 却找不到 | 在应用内检查 AppData 逻辑路径后，误认为外部进程也能读到同一文件 | 检测打包进程路径重定向；选择应用内外都验证可见的私有位置，复制后逐字节核对并保留原件 |
| 桌面找不到搜索工具 | 预检继承了 Codex 注入的 PATH，遗漏普通桌面环境 | 固定工具绝对路径；测试实际入口、最小 PATH 和无关 cwd，不能只测试 Python 内层函数 |
| 全量文件校验触发 180 秒限制 | 把本地大量文件哈希放进通用短超时子进程 | 将全量校验独立处理，分块读取、显示进度并检查读取稳定性；不放宽网络或业务请求超时 |
| 退出应用后文件清单变化 | 没预见 Codex 会增删自己的临时 Git 引用 | 对准备阶段差异逐项归因；改名前重新生成包含全部文件的清单，改名后不忽略任何临时引用 |
| 用户重启后收尾又被阻止 | 用最初准备时的启动时间要求跨多轮永远不变 | 历史基线与本轮运行基线分开；保留期间变化，并对本轮前后状态、身份和挂载严格比较 |
| Codex 更新后固定可执行路径失效 | 把一次安装的版本目录写死 | 从已核验安装根解析当前有效程序，验证版本和协议；缺失或有歧义时停止，不猜另一个路径 |
| 第二个聊天丢失研究目录范围 | 先设置资料根，再切 cwd；该版本切 cwd 自动移除了原 cwd 的访问范围 | 先保存 cwd，再用独立客户端保存最终资料根，第三个客户端无覆盖读取；覆盖“原 cwd 仍需作为资料保留”的情况 |
| 局部测试反复漏掉后半段 | 一个未加载聊天成功、预检成功，就让用户再次退出应用跑完整流程 | 先覆盖不同聊天状态和全部剩余阶段；把不可在线完成的最后动作压缩到最少，避免用用户重试代替验证 |
| “完成了”与实际结果不一致 | 终端中间提示容易被当作最终成功 | 用明确的阶段状态和最终标记，并核验目录存在性、完整哈希、聊天持久状态及服务健康 |
| Git 整理中的旧测试和换行误报 | 测试还匹配旧实现位置；字节保留型仓库的 CRLF 被默认空白检查误报 | 核对行为后修正过期测试，不能删掉保护性断言；按仓库约定识别 CRLF，避免重写部署字节 |

反复失败的共同原因是：**把当前进程、某个聊天或某一阶段的通过，推广成整个用户执行流程的通过。** 多次故障都在保护性检查处停止，避免了覆盖文件或破坏运行服务，但不能因此把反复让用户退出、执行、报错视为合格交付。应在交付入口之前验证真实外部环境和剩余阶段。

## 最终形成的方法

先建立对象和依赖清单，明确哪些迁入、哪些原位保留、哪些只是项目来源。准备恢复材料和外部执行工具，验证实际 CMD／PowerShell 入口。随后按当前版本支持的机制切换聊天 cwd 与来源范围，跨客户端确认持久化。需要关闭桌面时，把这一物理动作留到已验证工具的最终执行阶段。

每轮收尾重新记录当前运行基线；真正改名前取得严格全量清单，并再次确认写入者和依赖。改名后比对全部内容、运行状态和健康结果，重新打开桌面后再核对缓存及待应用项。记录部分完成状态，失败后从明确阶段恢复，而不是无条件全部重放。

匿名案例最终验证了相关聊天、新仓入口、归档前后文件内容及保留服务。研究资料仍独立，第三方子项目规范仍限于自身范围。后续代码提交与推送另行完成；这些结果没有自动授予数据库迁移、服务重建、删除备份或部署的权限。

## 使用与维护

在 Codex 中可直接请求：

> 使用 $codex-workspace-migration，把旧开发目录的相关聊天和开发入口迁到新仓库，核对运行依赖后归档旧目录；独立前端与研究资料仍保留。

技能正常参与自动发现。对于只改项目名称、只归档聊天、普通 Git 提交或业务数据库迁移，不需要套用整套流程。

这些错误在本次环境中有实际依据，不表示每个 Windows 安装都发生路径重定向、每个 Codex 版本都以同样顺序改变资料根。复用时先检查当前行为；不要将本次用户对运行环境、容器退役或分支推送的授权变成普遍规则。

修改校验器后运行：

```powershell
python -X utf8 '<skill-dir>/scripts/test_tree_manifest.py'
```

它使用合成临时目录，不操作真实聊天、容器、服务或业务数据。Windows 上生成和验证含中文的技能文件也应显式使用 UTF-8；不能把当前终端恰好可读当作跨进程编码验证。

## 开发与贡献

在仓库根目录运行 `python -X utf8 scripts/test_tree_manifest.py`。GitHub Actions 对 Windows 与 Linux、Python 3.10 与 3.14 运行相同合成测试；以工作流实际结果为准，平台不适用或权限不足的测试会明确标为跳过。

提交修复时说明适用系统、Python／Codex 版本和可复现的合成步骤。不要提交真实聊天标识、私有路径、凭据、业务资料或运行回执。当前版本的 Codex 行为必须重新核实；历史案例中的协议字段仅作为检索线索。
