# Codex 聊天目录与持久化

只有迁移包含 Codex 项目或聊天时读取。这里描述要验证的状态，不提供固定版本的全局数据库补丁。

## 能力发现与范围

先查看当前的项目、聊天列表和目标聊天状态，使用返回的准确名称和 ID。`move_thread_to_project` 等项目归属操作仅证明该操作实际返回的结果，不能推导磁盘 cwd 已迁移。选择目标时不读取无关聊天正文。

优先原生工具和当前界面。如果它们没有目录设置能力，先检查本机客户端帮助、当前协议 schema 和已安装代码；可用方法与参数都以当前版本为准。历史案例用过 `thread/settings/update`、`thread/resume` 与 `runtimeWorkspaceRoots`，这些名称仅是检索线索，不是可直接重放的 API 保证。

不要为了迁移启动模型回合、向其它聊天发送消息或改模型／审批配置。用户授权项目迁移不包含删除聊天和清空历史。

如果原生工具要求用户通过侧栏为聊天授予新增来源目录访问，遵循该要求，说明它来自工具的目录授权边界；不能通过离线写配置绕过。其余已经授权的备份、依赖检查和入口验证继续完成。

部分版本可能同时保留桌面旧项目 ID 映射和原生项目记录；原生 `thread/read` 返回 `projectId=null`，不一定代表桌面聊天未归属项目。分别核对当前映射、桌面归属及原生项目来源，不能为消除显示差异擅自重新分配聊天。

## 已归档聊天与历史记录

预检时明确区分未归档、已归档、被桌面加载及内部历史审查记录。不能只凭跨客户端返回 `notLoaded` 判断没有其它写入者，也不能只凭聊天标题判断记录类型。

已归档聊天可能允许只读元数据，但拒绝 `thread/resume`。保留原归档状态，不把恢复调用当作只读探针，不为预检自动解档。若已保存 cwd 和后续资料来源已符合目标，可只调整获准的项目／桌面来源关联，并核验归档记录未变；确实需要修改已归档的运行范围时，先核实当前支持的接口及范围。

按实际覆盖分别记录“运行范围已核验”和“归档元数据已核验”。只读 cwd、缓存或文件摘要不能替代尚未读取的运行设置，也不能把延后到退出桌面的检查报成通过。

历史内部审查记录中的旧 cwd、初始配置及旧路径文字可作为追溯保留。以原生来源类型、项目归属和加载／归档状态识别是否存在当前关联，不为达到“所有旧路径字符串消失”而删除记录或改写历史。

## 变更前快照

每个授权目标至少保留这些私有元数据：

- 项目 ID、聊天 ID、主机、当前活动／加载状态；
- 已保存 cwd、当前生效 cwd、项目来源及聊天资料范围；
- 已应用状态、待应用变更及其版本标记（如果当前实现存在）；
- 模型、推理配置、审批及权限策略中不应变化的字段。

为每个对象算出期望状态，不能只把旧路径做全局字符串替换。项目来源的顺序可能决定主目录，应按其语义保留；资料范围通常按规范化路径集合比较，但不能因此忽略缺失或额外授权。

## cwd 与资料范围的往返

历史案例发现：同一个客户端的立即回读可能返回旧状态；已加载对象的覆盖参数可能未持久化；切换 cwd 又可能自动移除原 cwd 的附加访问范围。当前版本先做最小验证，再决定是否使用以下顺序：

1. 保存目标 cwd，关闭该独立客户端，确认设置成功。
2. 在新的客户端中设置完整的预期资料范围，不再紧接着写一次 cwd。
3. 第三个客户端不传覆盖参数，读取最终 cwd、资料范围和不相关策略。

只读预检不要用可能持久化配置的恢复调用冒充读取。实际往返测试应是已获准迁移的一部分，使用明确的非活跃目标并保存前后状态；不能借测试更改无关聊天。

验证至少覆盖适用的真实情况：旧开发 cwd、原 cwd 需要保留为研究目录、已经在新目录、旧来源与无关项目并存。一个空闲目标的成功不能证明活跃主聊天可同时修改。

## 写锁、桌面缓存和关闭应用

空闲的聊天也可能被桌面持有。遇到写入者冲突，先完成不依赖关闭应用的检查，说明必须释放锁的具体原因；不要删除锁、抢占写入者或强制结束用户程序。

本机 API 成功不必然代表桌面缓存不会回写旧值。优先用原生界面或支持的机制处理待应用项；如果只能依赖版本绑定的离线状态处理，必须先核对 schema、备份、限定精确对象和字段，并证明其余状态未变。不要把某次 Electron 缓存结构复制为通用脚本，也不要直接批量修改未知数据库。

需要用户关闭桌面时，交付的收尾入口应已完成外部预检和可在线验证的实际往返。入口确认桌面已关闭后才做依赖写锁释放的步骤；用户重开后再独立核验，不能只信工具退出前读到的状态。

明确的 active-writer 拒绝且桌面仍打开时，可将该目标标记为“正常退出后核验”，继续其它独立检查；不能吞掉其它恢复错误，也不能把这一目标计入已经成功的往返。若没有任何可用目标完成实际往返，须明确说明覆盖限制。

## 部分完成与恢复

每个对象记录阶段与验证结果。若第三个聊天失败，前两个已经更新就是实际变更，报告应明确说明；目录仍未改名时也应明确说明。

恢复时重新读取全部目标：

- 与期望相等且验证完整的阶段跳过；
- 符合已记录中间状态的阶段从原处继续；
- 有用户新增来源、策略变化或未知状态时保留证据，不自动覆盖。

保留原始备份，每轮另取当前完整状态快照。重开桌面会更新未读、窗口和其它界面状态，跨轮整份状态字节不同不等于目录冲突；比较本次要改变的项目、cwd、来源、归属、待应用项与相关版本，保留其余当前值。真正落盘前仍检查本轮快照的原始字节未被并发修改。

已完成目标先独立回读，相等则跳过保存；桌面旧缓存恢复的已记录原范围属于可核对的中间状态，新出现的目录或授权不能当作同一种情况覆盖。模型和审批等非迁移字段沿用本轮当前设置，操作前后比较本轮值，不把旧备份中的偏好重放到用户的新设置。

出现部分完成故障后，验证剩余分支及完整恢复流程再交付入口。例如覆盖“部分聊天已保存、另一个已归档、桌面重开更新了界面状态”，并确认再次执行不会重复已完成写入；合成验证与实机验证的范围分别说明。

完成条件包含重开后的项目主目录、所有相关聊天 cwd、资料范围、不相关策略以及待应用状态。独立资料目录不应因为它仍在项目范围中，就被误记为已复制到新仓库。
